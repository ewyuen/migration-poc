## Context

SpecKit successfully generates test skeleton files with:
- Proper test class/method structure and attributes
- Gherkin scenario names as test method names
- Gherkin steps embedded as comments in Given/When/Then sections
- Placeholder test fixtures
- Generic implementations (dummy `Execute()` calls, `Should().NotBeNull()`)

The test writer agent runs as a post-processing step after SpecKit generates skeletons. It reads these skeletons, analyzes the embedded Gherkin comments, introspects the actual service implementations in the migrated code, and fills in the test method bodies with real code.

**Key constraint:** Focus on top-level use cases only—test the public APIs and happy paths, not exhaustive coverage of every method or internal logic.

## Goals / Non-Goals

**Goals:**
- Analyze SpecKit-generated test skeletons and extract Gherkin descriptions from comments
- Introspect migrated service code to discover available classes, methods, and types
- Translate Gherkin Given/When/Then steps into C#/Java/Python test code
- Generate proper test fixtures that initialize services with dependencies
- Create meaningful assertions based on Gherkin expectations
- Produce tests that can run immediately with realistic service interactions
- Support C#, Java, and Python test frameworks

**Non-Goals:**
- Generate exhaustive test coverage (all edge cases, all parameter combinations)
- Auto-generate service implementations (assumes they exist)
- Generate mocking/stubbing code (use existing test fixture setup)
- Modify SpecKit or change skeleton generation behavior
- Support languages beyond C# (Java and Python support deferred to future phases)

## Decisions

### Decision 1: Two-Phase Test Generation (Skeleton → Implementation)
**Chosen:** Separate SpecKit (skeleton) and test writer agent (implementation) into distinct phases
**Rationale:** 
- SpecKit handles structure (class/method layout, attributes, organization)
- Test writer handles semantics (understanding Gherkin, mapping to actual code)
- Each component has a clear, focused responsibility
- Allows skeleton generation to succeed even if service code is incomplete

**Alternatives considered:**
- Single-phase generation: Would require service code to exist during skeleton generation (ordering problem)
- Skeleton-only approach: Skeletons alone provide structure but no executable tests

### Decision 2: Comment-Based Gherkin Extraction
**Chosen:** Parse Gherkin descriptions from test method comments (as generated by SpecKit)
**Rationale:**
- SpecKit already embeds Gherkin steps in comments
- No need to re-parse feature files or coordinate file locations
- Comments are part of the test file, making context obvious
- Supports all three languages with same extraction approach

**Alternatives considered:**
- Re-parse original feature files: More authoritative but requires file discovery, harder to handle updates
- Store Gherkin in metadata/attributes: More structured but requires SpecKit changes

### Decision 3: Service Introspection via Reflection/Parsing
**Chosen:** Use language-specific reflection (C#), AST/reflection (Java), introspection (Python) to discover service classes, methods, and parameter types
**Rationale:**
- Service implementations already exist in migrated code
- Reflection is accurate and can extract actual parameter types and return types
- Avoids maintaining hand-coded mappings of service APIs

**Alternatives considered:**
- Parse config/documentation: Less reliable, easy to fall out of sync
- Hardcoded step mappings: Not scalable across different services

### Decision 4: Whitebox Testing (Access Internals)
**Chosen:** Tests call service classes directly; test fixtures create service instances with constructor injection
**Rationale:**
- Service implementations are in same package/namespace as tests
- Simpler setup than mocking external dependencies
- Tests can verify internal state (audit logs, side effects) if needed
- Aligns with user requirement ("whitebox tests")

**Alternatives considered:**
- Blackbox/API layer: Would require HTTP/RPC setup; more complex fixtures
- Full mocking: Defeats purpose of testing actual implementation

### Decision 5: Top-Level Use Cases Only
**Chosen:** Test public API entry points and happy paths; skip exhaustive edge case coverage
**Rationale:**
- User explicitly requested "only test top-level use cases"
- Reduces test generation scope and maintenance burden
- Focuses on scenarios described in Gherkin (which already cover key cases)
- Tests remain readable and focused

**Alternatives considered:**
- Exhaustive coverage: Too much generated code, hard to maintain
- Single happy path per scenario: Misses important edge cases already in Gherkin

### Decision 6: Gherkin Step to Code Mapping
**Chosen:** Use pattern matching (regex) to identify Gherkin step types and extract parameters, then generate C# code
**Rationale:**
- Step patterns from existing step mapper (StepRegistry)
- Parameters extracted from step text (e.g., "age 70" → `age = 70`)
- Mapping rules are configurable in speckit_config.yaml
- C#-focused reduces complexity while maintaining extensibility for future languages

**Alternatives considered:**
- Natural language processing: Too complex, unreliable parameter extraction
- Manual mapping per service: Not scalable

## Risks / Trade-offs

**[Risk] Service code doesn't exist yet → [Mitigation]** Agent fails gracefully and logs which tests couldn't be completed; skeleton remains for manual implementation

**[Risk] Parameter extraction from Gherkin text is ambiguous → [Mitigation]** Embed hints in Gherkin (e.g., "age 70" clearly means age parameter); document best practices

**[Risk] Assertion generation is too generic → [Mitigation]** Focus on high-value assertions (success/failure, key response fields); supplement with comments suggesting additional assertions

**[Risk] Whitebox tests become brittle if internals change → [Mitigation]** Test public API contracts, not internal implementation details; use stable property names

## Architecture

```
Test Writer Agent Workflow:
══════════════════════════════════════════════════════════════

┌─────────────────────────────────────────────────────────────┐
│ Input: SpecKit-generated skeleton test file (.cs/.java/.py) │
└────────────┬────────────────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. Extract Gherkin Comments                                 │
│    - Parse Arrange/Act/Assert sections                      │
│    - Extract Given/When/Then descriptions                   │
│    - Identify parameter values ("age 70", "email foo@bar")  │
└────────────┬────────────────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Service Code Introspection                               │
│    - Discover service classes in migrated output            │
│    - Map step patterns to actual methods                    │
│    - Extract parameter types from method signatures         │
└────────────┬────────────────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Translate Steps to Code                                  │
│    - Given → Arrange (create test data, setup)             │
│    - When → Act (call service method)                      │
│    - Then → Assert (verify results)                        │
└────────────┬────────────────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Generate Language-Specific Code                          │
│    - C#: Use FluentAssertions, proper namespaces           │
│    - Java: Use JUnit assertions, proper packages           │
│    - Python: Use pytest assertions, proper imports         │
└────────────┬────────────────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────────────────┐
│ Output: Test file with filled-in method bodies             │
│         Ready to run with actual service code              │
└─────────────────────────────────────────────────────────────┘
```

## Implementation Components

**TestWriterAgent** (new module)
- `read_skeleton_test()` - Parse generated C# test file
- `extract_gherkin_comments()` - Pull Given/When/Then from comments
- `extract_parameters()` - Parse test data from Gherkin text

**ServiceIntrospectorCSharp**
- Reflection-based discovery of C# service classes and methods
- Extract parameter types and return types from method signatures
- Locate service implementations in migrated output directory

**TestCodeFillerCSharp**
- `fill_arrange_section()` - Generate C# setup code from Given steps
- `fill_act_section()` - Generate C# method calls from When steps
- `fill_assert_section()` - Generate C# FluentAssertions from Then steps

**GherkinCodeMapper**
- Maps step patterns to C# code generation rules
- Extracts parameters from step text
- Coordinates C# test code generation

## Open Questions

1. Should test writer handle test fixture generation (TestFixture class) or assume SpecKit-generated fixture is sufficient?
   - **Current assumption:** Use SpecKit-generated fixture; agent only fills method bodies

2. How to handle Gherkin steps that don't map to obvious service methods?
   - **Approach:** Log as unmapped; generate TODO comment; test remains runnable

3. Should agent modify `speckit_config.yaml` step patterns or use existing mappings?
   - **Approach:** Use existing step registry; can extend via config before agent runs

4. How to handle test data validation (e.g., "invalid email")?
   - **Approach:** Use test input parameters directly; service validation will catch invalid data
