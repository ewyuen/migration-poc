## Context

The current OrchestratorV2 (`migration-poc/agents/orchestrator_v2.py`) orchestrates a 6-stage migration workflow:
1. Validation (check request validity)
2. Staging (copy component to run-scoped directory)
3. Exploration (LLM analyzes legacy code)
4. Modernization (LLM rewrites code with compilation verification)
5. BDD & Testing (generates and fills tests)
6. Verification (compile, run tests, collect coverage)

Currently, workflow state is threaded manually via a `WorkflowState` dictionary through a series of sequential method calls. Error handling, logging, and state transitions are all imperative. This works but makes the workflow topology invisible and observability requires manual instrumentation.

LangGraph provides a declarative state-graph abstraction: nodes represent units of work (stages), edges represent transitions with optional conditions, and state is a TypedDict schema. This unlocks built-in callbacks and tracing via OpenTelemetry, which Langfuse can consume.

## Goals / Non-Goals

**Goals:**
- Replace OrchestratorV2's manual state threading with LangGraph's StateGraph for clarity
- Define workflow topology explicitly as a directed graph (visualizable, debuggable)
- Instrument each node with OpenTelemetry spans (duration, status, errors)
- Integrate Langfuse via OTel span processor for end-to-end trace visibility
- Preserve all existing behavior: same error handling, same audit trail, same entry point interface
- Keep all agent code unchanged (agents stay as-is)
- Continue to verification even when intermediate stages fail (existing V2 behavior)

**Non-Goals:**
- Refactor or modify any existing agents (StagingAgent, explorer, modernizer, etc.)
- Change the 6-stage pipeline structure
- Add new migration logic or capabilities beyond orchestration
- Migrate existing V2 callers to V3 (both can coexist)

## Decisions

### 1. State Schema: Minimal Flow (Only What Next Node Needs)
**Decision**: Define MigrationState as a TypedDict with fields required by the next node, avoiding over-coupling.

**Rationale**: 
- Keeps state lightweight and explicit
- Forces thoughtful data flow design (what does modernization actually need from exploration?)
- Easier to test individual nodes in isolation

**Schema** (TypedDict):
```python
MigrationState:
  request: MigrationRequest           # Input, never changes
  run_id: str | None                  # Generated by stage_component
  stage: str                          # Current stage name (for logging)
  error: str | None                   # Error message if stage failed
  staging_results: dict | None        # Staging output (needed by explore)
  exploration_results: dict | None    # Explore output (needed by modernize)
  modernized_code: dict | None        # Modernize output (needed by BDD)
  bdd_tests: str | None               # BDD output (needed by test_writer)
  test_code: str | None               # Test output (needed by verify)
  verification_results: dict | None   # Final results
```

**Alternative considered**: Accumulate all intermediate outputs in state. Rejected because it couples stages unnecessarily and makes state a dumping ground.

### 2. Error Handling: Continue to Verification Regardless
**Decision**: Even if validation, staging, or modernization fails, flow continues to verification (which reports status, not crashes on it).

**Rationale**:
- Current V2 behavior (mark stage failed but continue to audit trail)
- Verification stage can report partial success (e.g., "staging failed, skipping tests, but recording in audit")
- Allows observability of full workflow even in failure paths

**Implementation**: Use conditional edges:
- If stage fails, set error in state and route to next stage (or skip to verification)
- Final verification stage handles "no prior state" gracefully (tests compiled but source modernization failed, etc.)

**Alternative considered**: Stop graph on first critical error. Rejected because user feedback wanted visibility into all stages regardless.

### 3. Entry Point: Same Interface as V2
**Decision**: `OrchestratorV3.orchestrate_migration(request: MigrationRequest) -> dict`

**Rationale**:
- Drop-in compatible; code calling V2 can call V3 with zero changes
- Same return dict structure (timestamp, stages, artifacts, status)

**Alternative considered**: Expose graph.invoke() directly. Rejected because users want familiar interface.

### 4. Audit Trail & Logging
**Decision**: Preserve `orchestrator.jsonl` with same format; OpenTelemetry traces are separate (not replacing).

**Rationale**:
- JSONL audit trail is already a dependency (e.g., compliance logs)
- OTel traces are for observability/Langfuse, not audit
- Both coexist: JSONL for record, OTel for visualization

**Implementation**: After graph completes, V3 writes final state dict to `orchestrator.jsonl` just like V2 does.

### 5. OpenTelemetry Instrumentation: Node Level
**Decision**: Each graph node is wrapped in an OTel span.

**Rationale**:
- Simple, clear: one span per stage
- Captures duration, status, and any exceptions
- Enough granularity for Langfuse dashboard
- Agent-level instrumentation deferred (can add later if needed)

**Structure**:
```
Root span: orchestrate_migration
├── node_validate (span)
├── node_stage (span)
├── node_explore (span)
├── node_modernize (span)
├── node_bdd_and_test (span)
└── node_verify (span)
```

**Alternative considered**: Span per LLM call inside agents. Rejected because agents aren't modified (would require agent changes); node-level spans are sufficient for workflow observability.

### 6. Langfuse Integration
**Decision**: Export OTel traces to Langfuse via LangfuseSpanProcessor (OTLP gRPC exporter).

**Rationale**:
- Langfuse has built-in OTel span processor; no custom bridge code needed
- Traces arrive at Langfuse in real-time (gRPC streaming)
- Langfuse dashboard shows full trace waterfall, latencies, errors

**Configuration**:
- Create tracer provider with OTLP exporter
- Add LangfuseSpanProcessor
- Pass tracer to OrchestratorV3
- LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY from env

**Alternative considered**: Use Langfuse SDK directly (no OTel). Rejected because OTel is standardized, not Langfuse-specific; lets us swap exporters later.

### 7. Dependencies
**Decision**: Add to requirements.txt:
```
langgraph>=0.1.0
opentelemetry-api>=1.20.0
opentelemetry-sdk>=1.20.0
opentelemetry-exporter-otlp>=0.41b0
langfuse>=2.0.0
```

**Rationale**:
- LangGraph for orchestration primitives
- OpenTelemetry for tracing (API, SDK, OTLP exporter)
- Langfuse for trace collection and UI

## Risks / Trade-offs

**Risk 1: LangGraph API churn (v0.x)**
- Mitigation: Pin version; monitor releases; LangGraph 1.0 will have stability guarantee. For now, accept pinned dependency.

**Risk 2: OTel overhead (spans per node)**
- Mitigation: Low overhead for 6 nodes. If performance matters, add sampling config later.

**Risk 3: Langfuse SaaS cost**
- Mitigation: Use local OTLP collector if cost is concern (Langfuse can subscribe to local endpoint). Out of scope for this change.

**Risk 4: Existing V2 code not automatically migrated**
- Mitigation: V3 is opt-in; V2 stays as-is. Callers can migrate incrementally or run both in parallel. Not a breaking change.

## Migration Plan

1. Create `orchestrator_v3.py` alongside `orchestrator_v2.py`
2. Add dependencies to requirements.txt
3. Update tests to cover OrchestratorV3 (both happy path and error paths)
4. Deploy as new optional entry point (no forced migration)
5. Monitor Langfuse dashboard for workflow traces
6. V2 can be deprecated in a future release (not this one)

## Open Questions

1. Should we auto-retry failed nodes (e.g., if modernization fails, retry with different prompt)? Current design does not. Deferred to future phase if needed.
2. Should OrchestratorV3 support parallel node execution (e.g., explore and stage in parallel)? Current design is sequential. Can add if architecture supports it later.
