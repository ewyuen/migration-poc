## Purpose

The test writer agent is a post-processing component that fills in C# test implementations after SpecKit generates skeleton test files. It reads Gherkin descriptions embedded in test file comments, analyzes actual C# service implementations, translates Gherkin steps into executable code, and produces working NUnit tests that exercise top-level use cases.

## Requirements

### Requirement: Read and parse SpecKit-generated C# test skeleton files
The system SHALL locate SpecKit-generated C# test skeleton files (*.cs) in the migrated service directories and extract the test method structure with embedded Gherkin comments.

#### Scenario: Successfully read C# test skeleton
- **WHEN** test writer processes a C# test file generated by SpecKit
- **THEN** system extracts test class name, test method names, and Gherkin comments from Arrange/Act/Assert sections

### Requirement: Extract Gherkin steps from test method comments
The system SHALL parse Given/When/Then steps from test method comments and extract test data parameters embedded in the Gherkin descriptions.

#### Scenario: Extract Given step with parameter values
- **WHEN** a test comment contains "Given a user with email 'doctor@clinic.com' and password 'SecurePass123'"
- **THEN** system extracts email and password as parameter values for test setup

#### Scenario: Extract When step describing action
- **WHEN** a test comment contains "When I authenticate the user"
- **THEN** system identifies the action as "authenticate_user" and maps it to a service method

#### Scenario: Extract Then step with expected outcomes
- **WHEN** a test comment contains "Then the authentication should succeed" and "And a valid session token should be returned"
- **THEN** system extracts expected outcomes (success, token presence) as assertion requirements

### Requirement: Introspect migrated C# service code
The system SHALL analyze the migrated C# service implementation to discover available classes, public methods, constructors, and parameter types.

#### Scenario: Discover service classes in C#
- **WHEN** test writer processes a C# service migration
- **THEN** system uses reflection to locate public classes (services, domain models, etc.) and their public methods

#### Scenario: Extract method parameter types
- **WHEN** test writer analyzes a C# service method
- **THEN** system extracts parameter types and return types for proper type conversion

### Requirement: Translate Gherkin steps to C# test code
The system SHALL convert Given/When/Then steps into corresponding C# test code sections: Arrange (setup), Act (method call), Assert (verification).

#### Scenario: Translate Given step to Arrange code
- **WHEN** a Given step specifies test data (e.g., "a user with email foo@bar and password Pass123")
- **THEN** generated C# code creates a test object with those values (e.g., `var request = new AuthenticationRequest("foo@bar", "Pass123")`)

#### Scenario: Translate When step to Act code
- **WHEN** a When step describes an action (e.g., "I authenticate the user")
- **THEN** generated C# code calls the corresponding service method (e.g., `var result = service.Authenticate(request)`)

#### Scenario: Translate Then step to Assert code
- **WHEN** a Then step describes an expected outcome (e.g., "the authentication should succeed")
- **THEN** generated C# code includes an assertion verifying that outcome (e.g., `result.IsSuccess.Should().BeTrue()`)

### Requirement: Generate valid C# NUnit test implementations
The system SHALL generate valid, executable C# test code using NUnit framework and FluentAssertions library.

#### Scenario: Generate C# test with NUnit and FluentAssertions
- **WHEN** test writer fills a C# test method
- **THEN** generated code uses [Test] attributes, C# idioms, proper namespaces, and FluentAssertions for assertions

#### Scenario: Generate proper C# imports and namespaces
- **WHEN** test writer generates a C# test method
- **THEN** generated code includes appropriate using statements and test class inherits from proper base class

### Requirement: Create C# test fixtures with proper service initialization
The system SHALL generate or update C# test fixture classes that initialize services with required dependencies.

#### Scenario: Create C# test fixture
- **WHEN** test writer processes a C# test file without a proper fixture
- **THEN** system generates a TestFixture class with method `CreateSystemUnderTest()` that instantiates the service

#### Scenario: Inject dependencies in fixture
- **WHEN** test writer creates a service instance
- **THEN** system provides constructor with required dependencies (actual or test doubles)

### Requirement: Map Gherkin parameters to C# method parameters
The system SHALL extract parameter values from Gherkin descriptions and map them to actual C# service method parameters with correct types.

#### Scenario: Extract numeric parameters
- **WHEN** a Gherkin step says "a patient age 70"
- **THEN** system extracts "70" as an integer and uses it in the service call with correct C# type (int)

#### Scenario: Extract string parameters
- **WHEN** a Gherkin step says "email 'doctor@clinic.com'"
- **THEN** system extracts "doctor@clinic.com" as a string and uses it in the service call

#### Scenario: Extract currency parameters
- **WHEN** a Gherkin step says "treatment cost $100.00"
- **THEN** system extracts 100.00 as a decimal and uses it in the service call with correct C# type (decimal)

### Requirement: Generate meaningful C# assertions from Gherkin expectations
The system SHALL create FluentAssertions that verify the expected outcomes described in Gherkin Then steps.

#### Scenario: Assert success outcome
- **WHEN** a Then step says "the authentication should succeed"
- **THEN** generated C# code includes assertion verifying success (e.g., `result.IsSuccess.Should().BeTrue()`)

#### Scenario: Assert specific value in response
- **WHEN** a Then step says "the discount amount should be $15.00"
- **THEN** generated C# code includes FluentAssertions verifying the discount value

#### Scenario: Assert error message
- **WHEN** a Then step says "the authentication should fail with error 'Invalid email format'"
- **THEN** generated C# code includes assertion verifying the error message

### Requirement: Handle unmapped or ambiguous steps gracefully
The system SHALL generate runnable C# test code even when Gherkin steps don't perfectly map to service methods, using TODO comments to guide manual completion.

#### Scenario: Unmapped Gherkin step
- **WHEN** a Gherkin step doesn't match any known C# service method pattern
- **THEN** system generates a TODO comment in the C# test with the unmapped step text, allowing the test to compile/run

#### Scenario: Ambiguous parameter extraction
- **WHEN** a Gherkin step contains parameter values but the extraction is ambiguous
- **THEN** system generates C# code with extracted best guess and adds TODO comment for manual review

### Requirement: Support top-level use case testing only
The system SHALL focus on testing public API entry points and happy paths, not exhaustive edge case or unit-level coverage of every method.

#### Scenario: Test public service method
- **WHEN** a Gherkin scenario describes calling a public C# service method
- **THEN** system generates test that calls that public method directly

#### Scenario: Skip internal method testing
- **WHEN** a Gherkin scenario could test an internal/private C# method
- **THEN** system focuses on testing through the public API instead, ignoring internal implementation details

#### Scenario: Test happy path and critical failures
- **WHEN** processing a Gherkin scenario set (happy path + validation failures)
- **THEN** system generates tests for the happy path and critical validation failures, not every possible error condition

### Requirement: Integrate with orchestrator pipeline
The system SHALL be callable as a stage after SpecKit test generation, accepting C# migrated service components and producing fully-implemented C# test files.

#### Scenario: Invoke test writer as pipeline stage
- **WHEN** orchestrator completes SpecKit skeleton generation
- **THEN** test writer stage is called with component name and base output directory

#### Scenario: Report results and errors
- **WHEN** test writer completes processing
- **THEN** system returns status (success/partial/failed), list of filled tests, and any errors encountered

#### Scenario: Continue on unmappable tests
- **WHEN** test writer encounters a C# test that cannot be filled due to missing service code
- **THEN** system logs warning, leaves skeleton intact, and continues with other tests
